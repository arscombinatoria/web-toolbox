Toolchain
---------
Emscripten SDK 4.0.20 Linux/amd64 container:
emscripten/emsdk@sha256:33e992367f721747d8008c9141c04fa017139e3557a60e0c80be93a0870fe462
Build flags: Release, -O3, SIMD128, LTO, standalone Wasm, single-threaded,
growing memory with a 1 GiB maximum. The build runs offline after archive
SHA-256 verification and compares two fresh builds byte-for-byte. The wrapper
uses Wasm C++ exceptions for safe cleanup through JPEGli's vector-backed work;
the build applies `wasm-exceptions.patch` to replace JPEGli's default
`-fno-exceptions` with `-fwasm-exceptions` for the library objects.

The JavaScript interface uses only `malloc`, `free`, the `jpegli_encode` wrapper,
Wasm memory, and standalone Wasm initialization. Encoder output memory belongs
to the caller and must be released with `free` after use.

The linker also includes Emscripten's LLVM libunwind legacy-exception support
and dlmalloc 2.8.6. See LICENSE.libunwind, CREDITS.libunwind, and
COPYRIGHT.dlmalloc.

Security review scope
---------------------
The shipped artifact is an encoder-only JPEGli build. The decoder, command-line
tools, tests, benchmarks, libjpeg-turbo implementation, and skcms implementation
are not linked. On 2026-11-27, the upstream GitHub Security Advisories endpoint
reported no published advisories for the pinned JPEGli, Highway, or libjpeg-turbo
repositories. The OSV API was queried by pinned Git commit for JPEGli and
Highway; both queries returned no matching advisories. This is a scoped
public-advisory check, not a claim that the code has no vulnerabilities.
