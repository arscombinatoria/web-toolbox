# SSIMULACRA2 のブラウザ実行可能性

検証日 2026-11-22（JST）。対象は `arscombinatoria/web-toolbox` の `main`、`730b2ba2be13ccb503292a3c2af64cdb180445c6` です。手順と自動検証は [PoC の README](./README.md) を参照してください。

**結論は条件付きで採用可能**です。上限を1,048,576画素から検討し、利用者が明示的に実行する参考スコアとして導入できます。透過保持形式と品質の自動判定は追加検証が必要です。

## 既存実装との関係

`AGENTS.md`、`docs/architecture.md`、画像変換の `index.ts`・`encoder.ts`、Registry、Vite、Playwright、Pages のワークフローを確認しました。現行 UI は元画像を基準に左右へ独立したエンコーダー設定を持ち、ブラウザ標準 Canvas で JPEG（白背景）と PNG（透過保持）を生成します。画像入力制限は各辺8,192 px、1,600万画素、32 MiB です。Vite と Playwright は `/web-toolbox/` を使用し、既存の画像変換 E2E は Chromium と Firefox が対象です。PoC は同じ Vite の base を独立したルートで使います。 [基準コミット](https://github.com/arscombinatoria/web-toolbox/tree/730b2ba2be13ccb503292a3c2af64cdb180445c6)

## 比較方法

Worker は写真・単色・グラデーション・透明グラデーションから同寸法の画像を作ります。JPEG は白（`#fff`）に合成してエンコードし、出力をデコードして比較します。PNG はアルファを保持して可逆エンコード・デコードし、スコア計算前に元画像・出力画像とも白に合成します。Canvas の `colorSpace: 'srgb'` で得た8ビット RGBA を採点アダプターが RGB に詰め替えます。アルファそのものや透明部分に隠れた RGB は計測対象外です。PoC のエンコードは Worker の OffscreenCanvas を使います。現行 UI の HTMLCanvasElement とエンコード結果が一致するかは確認していません。

公式値は libjxl **v0.13.0**（`5a7da83447212fe4900fc29ce97430b881caa67e`）の Linux x86_64 公式静的 CLI で計算しました。各ブラウザが Wasm に渡した RGB を P6 PPM で書き出し、CLI で同じ順に比較します。libjxl はこの PPM を sRGB と解釈します。CLI に未合成の透明画像を渡すと、参照画像にアルファがある場合は 0.1 と 0.9 の背景で評価し、低い方を返します。ここでは先に白へ合成した同一 RGB を使うため、二背景のアルファ評価は対象外です。 [CLI の公開リリース](https://github.com/libjxl/libjxl/releases/tag/v0.13.0) · [CLI のアルファ処理](https://github.com/libjxl/libjxl/blob/v0.13.0/tools/ssimulacra2_main.cc) · [sRGB の既定値](https://github.com/libjxl/libjxl/blob/v0.13.0/lib/extras/dec/color_hints.cc#L65)

## ブラウザ互換性

Playwright 1.65.1 の headless Chromium **159.0.8154.6** と Firefox **159.0** で、Vite 8.3.8 が出力した静的ファイルをループバックの **`/web-toolbox/`** から読み込みました。ハッシュ付き Worker と `application/wasm` のアセットが同じベースパスで解決され、Worker 内で採点できました。リクエストはローカルアセットへの GET です。実際の GitHub Pages の配信は未検証です。

両ブラウザで Wasm の HTTP 503、最小寸法未満、1,600万画素超、不明な変換形式がエラーになりました。最大サイズの採点中に「中止」を2回実行し、その後に採点を再開できました。各ブラウザで Worker の生成・`terminate()` 呼び出し・Playwright の終了イベントをそれぞれ25回確認し、残存 Worker は0本でした。

Firefox の既定起動ではこの環境のコンテンツプロセスがクラッシュしました。実測ではブラウザ同梱の共有ライブラリを優先する `LD_LIBRARY_PATH` と、ローカル検証プロセスに限定した `MOZ_DISABLE_CONTENT_SANDBOX=1` を使用しました。アプリや PoC の起動コードにこの設定を組み込んでいません。

PoC の型チェック・Vite ビルド・ブラウザ検証が完了しました。本番エントリのビルド、既存の単体テスト561件、バッジテスト11件、既存 E2E 103件も通過しました。

## 採用条件と実装方針

現行ツールの許容サイズ全域で自動採点する設計は、計算時間とメモリの点で見送ります。公式値との互換が必要な用途や、採点結果で品質閾値を自動判定する用途は、単色の差を解明し、広いコーパスで許容差を決めてから判断します。

1. 元画像を参照し、左右各エンコーダーの実際の出力 Blob を評価します。変換・表示・保存と独立した操作とし、同一設定で共有した出力は採点も再利用します。入力や設定の変更時に旧ジョブを終了し、古い結果の反映は世代番号で防ぎます。採点が失敗しても画像変換と保存は利用できる構成にします。
2. 単一の Worker を必要時だけ作成し、採点は直列化します。最初の上限候補は **1,048,576画素（1 Mi画素）**とし、モバイル相当の端末を測定して引き下げも検討します。寸法と画素数を採点用 Canvas の確保前に判定します。縮小採点を追加する場合は明示操作とし、左右を同じフィルタ・寸法で縮小して採点解像度を表示します。元解像度の値との混用を避けます。
3. 0.1.0 の Wasm とハッシュを固定し、アダプターには ABI、バッファ境界、有限値、色空間、終了の回帰検証を持たせます。Wasm は同一オリジンから遅延ロードします。依存更新ごとに両ブラウザと公式値で再検証します。公開前にライセンス表示を確定します。
4. 透明 JPEG の比較条件は現行エンコーダーに合わせて白背景と表示します。透過保持形式はブラウザ間の差を解消・説明できるまで初期対象から外します。対応を広げる場合は、暗色・明色の両背景での比較や、アルファ面の別評価を仕様として決めます。WebP、AVIF、MozJPEG は出力を同寸法の8ビット sRGB にデコードできれば同じ採点器を使えます。AVIF の HDR・広色域、ICC、EXIF 向き、透過、アニメーション、ブラウザごとのデコーダー差は個別に検証が必要です。

### 別実装の選択肢

- `calc-s2-rust@1.0.3` にはブラウザ用 wasm-bindgen API があり、Wasm は84,615バイトです。公開ソースは 2022 年の `yuvxyb 0.3` 系と内包した採点実装を使い、2.1 との数値互換は確認できませんでした。今回の時間・メモリの対策として、そのまま置き換える根拠は得ていません。 [npm](https://registry.npmjs.org/calc-s2-rust/1.0.3) · [公開ソース](https://github.com/iola1999/calc-s2-rust)
- 公式値との整合を最優先する場合は libjxl C++ の採点器を Wasm にビルドする案があります。サイズ、SIMD、メモリと再配布条件は別途測定が必要です。SSIM は構造類似度だけで足りる場合の候補です。SSIMULACRA 2.1 のぼけ・リンギングの評価やスコア尺度とは異なり、指標・閾値を選び直す必要があります。両案の Wasm 性能は未測定です。 [公式アルゴリズム](https://github.com/cloudinary/ssimulacra2/tree/v2.1#how-it-works)

### 残る技術リスク

単色での公式値との差、8ビット sRGB への正規化時の色管理と透過仕様、低メモリ端末での上限、安全なタイムアウト、将来の Wasm ABI 変更が残ります。実機モバイル、Safari、実際の GitHub Pages、強制 OOM、長時間反復による物理メモリの解放は未検証です。今回の写真は1種で、性能測定には同じ画像を各解像度へ拡大・縮小しています。大きい画像の正確性は有限値と反復一致を確認し、公式 CLI との比較は512×512画素相当以下に限定しました。
